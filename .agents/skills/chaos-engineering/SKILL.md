# Chaos Engineering & Resilience Verification Skill

本スキルは、オンプレミス・閉域網環境（ytagarasu）およびエージェント開発組織・実行ハーネスに対して、意図的かつ制御された障害注入（カオス実験）を行い、自己修復機能、プロセスマネージャの耐障害性、縮退運転、および組織ハーネスの継続性を監査・検証するためのプロトコルである。

---

## 1. カオスエンジニアの役割と責務

カオスエンジニア（Chaos Engineering Specialist）は、「システムは必ず壊れる」という前提に立ち、プロダクションや本番運用で起こり得る偶発的・致命的な障害を意図的に引き起こすことで、システムの弱点を事前に発見・解消する。

### 核心責務
1. **定常状態の定義と計測**: 実験前の正常稼働状態（プロセス稼働、ヘルスチェック、応答レイテンシ）を明確にする。
2. **安全な障害注入**: 制御された範囲（Blast Radius）で障害を発生させ、無関係な環境破壊を防ぐ。
3. **自己修復・縮退運転の検証**: 障害発生時に、スーパーバイザー（監視機構）やハーネスが自動で自己修復・再起動・安全停止できるかを検証する。
4. **実験レポートと改善チケットの創出**: 障害注入の合否（Pass/Fail）、MTTR（平均復旧時間）、発見された不具合をエビデンスとして記録し、Issueとして還元する。

## 2. 障害注入カタログ（Chaos Fault Catalog）

| 障害コード | 障害名 | 注入手段 | 期待される挙動（Pass条件） |
| :--- | :--- | :--- | :--- |
| **CHAOS-01** | プロセス突然死（SIGKILL） | `kill -9 <PID>` による子プロセス即時停止 | スーパーバイザーが即時（設定秒数以内）に検知し、バックオフを伴って自動再起動する。孤児プロセスを残さない。 |
| **CHAOS-02** | ポート競合（EADDRINUSE） | 使用ポートを一時ダミープロセスで占有 | ポート競合を検知して安全に待機またはエラーログを記録し、ポート解放後に正常バインド・起動する。パニックを起こさない。 |
| **CHAOS-03** | ロックファイル残留（Dirty State） | プロセス不在のPIDファイル／ロックファイルを配置 | 該当PIDの生存有無（`kill -0`）を照合し、ゾンビロックを検知して安全にパージ・再取得する。 |
| **CHAOS-04** | 設定・マニフェスト破損 | 構文不正なYAML/JSONへの書き換え | 不正設定を拒絶し、前回正常稼働状態を維持するか、明瞭なエラーメッセージを出力して終了する。中途半端な状態で起動しない。 |
| **CHAOS-05** | ハーネス外乱・ループ誘発 | テスト失敗の連続発生、不正コマンドの混入 | サーキットブレーカー（`loop-detection-circuit-breaker`）が正しく発動し、無限ループを停止して安全にエスカレーションする。 |

## 3. カオス実験の実行プロトコル（5段階フロー）

カオス実験を実施する際は、以下の5段階を順守する。

```
[Phase 1: ベースライン確認]
       │ (正常稼働、PID、ポート、メトリクス確認)
       ▼
[Phase 2: 障害注入 (Fault Injection)]
       │ (kill -9, ポート占有, 破損ファイル配置 等)
       ▼
[Phase 3: 耐性・自己修復の観測]
       │ (スーパーバイザーの検知、自動再起動、ログ記録)
       ▼
[Phase 4: 原状復帰 & クリーンアップ]
       │ (注入障害の解除、残留プロセス・ファイルの全清掃)
       ▼
[Phase 5: エビデンスレポート記録]
         (evidence/chaos-experiment-<id>.md に詳細記録)
```

### Phase 1: ベースライン確認（Steady State Verification）
- 対象サービス・プロセスのステータスが `RUNNING` であることを確認。
- ヘルスチェックエンドポイントまたは監視コマンドが `OK` を返すことを記録。

### Phase 2: 障害注入（Fault Injection）
- 事前に定義した爆発半径（指定プロセス、指定ポート、指定テンポラリディレクトリ）に限定して障害を注入する。
- 注入開始時刻をミリ秒精度で記録する。

### Phase 3: 耐性・自己修復の観測（Resilience & Self-Healing Observation）
- 想定時間（例: 5秒〜10秒以内）に対象が自動復旧するか観測する。
- 観測指標:
  - プロセス生存確認（新しいPIDでの再起動）
  - ログ出力（障害検知ログ、リカバリログの存在）
  - 二重起動やゾンビプロセスの不在

### Phase 4: 原状復帰（Rollback & Cleanup）
- 実験用に作成したダミープロセス、ポート占有リスナー、一時破損ファイルを完全に削除する。
- システム全体が実験前の安定状態（Steady State）に戻ったことを確認する。

### Phase 5: エビデンスレポート出力
- `evidence/chaos-experiment-<YYYYMMDD-HHmmss>.md` に実験ログ、コマンド実行結果、判定（PASS/FAIL）を書き出す。

## 4. 安全停止規則（Emergency Kill-Switch）

カオス実験中に以下の異常が認められた場合、カオスエンジニアは即座に実験を中止（Abort）し、全プロセスのクリーンアップを実施しなければならない。

1. **爆発半径の逸脱**: 対象外の無関係なプロセス（例: git, IDE, OS基盤）に影響が波及したとき。
2. **CPU/メモリの無限高騰**: 再起動ループによるCPU 100%継続やメモリリークが発生したとき。
3. **5分以上の自己修復不能**: 設定タイムアウトを超えて復旧せず、手動介入が必要となったとき。

中止時は直ちに `evidence/chaos-abort-<timestamp>.md` を残し、原因をIssueとして起票する。
